# TYPE-MOON-WORLD 英灵设计规则

适用于本 MOD 的新英灵设计、旧英灵重置、玩家从者卡与召唤实体的能力设计。基线整理于 2026-10-18，来自织田信长首轮重置讨论。本文件规定设计方法；单个角色的技能数值不自动成为所有英灵的公共规则。

配套文件：[AI 提示词与输出模板](servant_design_template.md)、[织田信长设计案例](servant_design_oda_nobunaga_baseline.md)。代码落地另参考项目 `docs/servant_creation_example.md` 和 `docs/servant_ai_creation_guide.md`。

## 1. 依据、范围与设计状态

- 先确定角色、职阶、作品版本和本轮工作范围。同名不同职阶、不同灵基、不同作品时期的数据不能混拼。
- 当前用户明确选择优先；其次沿用已确认的本地设计。原作资料提供人物和能力依据，现有源码提供当前行为事实，两者均不能覆盖用户的改编要求。
- FGO Wiki 等资料站应注明链接和引用的作品或资料条目。查不到的设定标为未核实，不把原创设计写成原作事实。
- 每项重要规则标注为“用户已确认”“方案默认”或“待确认”。默认值应给理由；高影响矛盾应列出具体选项，不能暗中选一个数值。
- 重置按用户指定角色逐个进行。共用规则可以抽象，但不借此重做其他英灵的技能、数值和 AI。
- 设计稿、实际实现、已测试结果分别记录。文档写入设计不等于功能已经实现；源码旧行为也不等于新设计必须保留。

## 2. 从设定到 MC 能力

采用“人物与能力依据 → 本地被动／操作技能／特殊机制／宝具 → 可验证的游戏行为”的设计方式。

- 不必保留 FGO 的三个主动技能结构。一个原作技能可以拆成多个操作技能，也可以改为常驻被动；多个动作也可以共享一个设定来源。
- 职阶技能需要记录，一般作为被动处理。保有技能记录其设定来源和最终本地形态，不重复保留一套无实际用途的 FGO 持有技能面板。
- **FGO 追加技能完全排除**：不记录、不借用其数值，也不以“换个名字”的方式加入攻击适性、魔力装填等效果。角色有独立设定依据的同类能力须写明该依据。
- 不直接搬入指令卡性能、暴击星、NP 获得率、Over Charge 档位、回合数、再临和技能等级成长。若需要转成 MC 机制，应重新说明用途、触发条件和具体数值。
- 技能数量服从角色能力和操作需要，不强制填满槽位。禁止仅为补槽位发明没有依据或重复的伤害技能。
- 每个技能至少说明它在战斗中解决什么问题，例如近战脱身、定点压制、追击、破防、爆发或领域控制；强度应与消耗、命中难度、持续时间和可反制方式相匹配。

## 3. 身份、特性与时代

### 3.1 分开记录的字段

| 字段 | 含义 | 设计要求 |
| --- | --- | --- |
| 真名与角色标识 | 唯一角色记录 | 给出中文名、可用外文名及稳定 id |
| 职阶 | Saber、Archer 等 | 职阶身份独立于人物特性 |
| 天地人星兽 | 本 MOD 的阵营／副属性 | 不与善恶或秩序倾向混写 |
| 秩序轴 | 秩序、中立、混沌 | 与道德轴分开判定 |
| 道德轴 | 善、中庸、恶等 | 中庸不等于秩序轴的中立 |
| 人物特性 | 女性、王、人型、神性等 | 每一项有依据，不能从模型外观随意推导 |
| 时代 | 神话至未来 | 独立元数据，不直接给所有英灵增减伤 |

“人”副属性、“人型”、“人科从者”、“活人”是不同概念。拥有其中一项不能自动补齐其他项。“王”也不自动附送王权、魅力、统率等数值效果。

本项目的中庸键为 `balanced`，秩序轴中立为 `neutral_alignment`；人科从者为 `human_kind`，七骑士的从者为 `seven_knights`。其他新增键落地前核对项目实际枚举，不臆造已经存在的接口。

人物特性与动作标签分别记录：`王` 是人物特性，`projectile`／`area`／`interrupt` 等是动作标签。范围攻击、投射物等动作标签不能代替宝具分类。

### 3.2 六种时代

| 中文名 | 数据键 | 已约定的现有英灵归属 |
| --- | --- | --- |
| 神话 | `mythology` | 阿拉什、吉尔伽美什（Archer／Caster）、恩奇都、库丘林、迪尔姆德、赫拉克勒斯、美狄亚、美杜莎、芭万希、苍白骑士、阿尔托莉雅、高文、兰斯洛特，共14位 |
| 古代 | `ancient` | 伊斯坎达尔、赵云、牛若丸、蓝胡子、黑贞、咒腕、百貌、幽弋、狂信子，共9位 |
| 大航海 | `age_of_sail` | 织田信长、佐佐木小次郎、千子村正、帕拉塞尔苏斯，共4位 |
| 近现代 | `early_modern` | 冲田总司、南丁格尔、李书文，共3位 |
| 现代 | `modern` | 暂无 |
| 未来 | `future` | 红A（Emiya Archer） |

以上归属采用本 MOD 已约定口径，不依据历史年表自行挪动。新英灵的时代需要给出选择依据。缺失时代应标为未知，不能仅因代码存在 `modern` 回退值，就在设计上认定目标属于现代。

时代可被“针对神秘”的能力读取，但**不自带公共时代克制**。信长的时代伤害表属于天下布武，不能套到其他英灵的所有攻击上。

## 4. 基础参数与等级

- 记录筋力、耐久、敏捷、魔力、幸运、宝具六项。注明采用哪个作品版本；用户指定帝都等版本时，不改回 FGO 面板。
- 当前基础参数 E／D／C／B／A 的系数为10／20／30／40／50。应调用项目公共参数换算，不为单个角色再写一套生命、护甲或魔力公式。
- 本次明确的基础参数符号规则：单个 `+` 是该等级系数×2，单个 `-` 是该等级系数÷2。例如A+为100，A-为25。当前A++沿用已有×3规则，不当作两次×2。
- 等级字母与数值倍率分别保留。A-的计算结果较低，不意味着资料显示要改成C或D。其他未约定的多重减号、特殊组合应单独确认。
- 宝具的 `E～EX` 等范围等级要原样记录并说明可变条件；EX不是“比A固定多一级”的通用数值系数。
- **基础参数等级、技能等级、神性等级不是同一套换算。** 不把A-参数÷2机械套到战略减伤、神性特攻、对魔力或技能持续时间上。

## 5. 被动与增伤必须有来源

每个被动记录：名称、等级、职阶／保有分类、设定依据、触发条件、作用对象、数值、叠加规则及失效条件。只有设定占位的被动明确写“无数值效果”，不偷偷补强。

- 所有增伤、减伤、免疫、破防、恢复、速度加成必须归属到明确的被动、主动、宝具或已存在的公共战斗规则。
- 人物资料里不再额外建立一份“看到某标签就乘1.5”的隐藏特攻列表。即使代码复用标签判定，也必须能追溯到具体能力。
- 同一能力已在公共伤害入口结算时，不能又在射击、枪实体、子弹命中、卡牌或 NPC Helper 中重复乘算。
- “独立行动”的设计语义仅影响失去御主后的现界时间，不额外提供随机增伤或暴击威力；重置时复用已有契约／现界系统。此规范本身不授权批量修改尚未重置的其他英灵。
- 不把所有“对神性有利”效果都写成伤害倍率。额外攻击、破防、击退、状态清除分别记录，不能互相冒充。

### 战略的可复用本地方案

战略作为被动，在自己使用对军／对城宝具，以及承受对军／对城宝具时提供修正。整理方案默认采用E／D／C／B／A分别4%／8%／12%／16%／20%的增伤与同档减伤，A封顶20%。该阶梯属于本地设计默认，后续用户可以调整。

判定依赖实际宝具分类。普通范围技能不算对军宝具，对神、对人、结界等宝具也不因伤害范围大而自动符合。

## 6. 伤害、命中与特攻的书写要求

### 6.1 数值口径

- 20ticks=1秒；1点生命／伤害为MC的1点，即半颗心。距离用格，速度注明格/tick或其他实际单位，魔力使用MP。
- 技能先列基础伤害，再列角色被动、状态增益、宝具修正及目标防御，禁止把特攻后的数字冒充基础伤害。
- 物理、投射物、火焰、魔法、爆炸等伤害类型要明确，并说明是否受护甲、魔抗、抗火等现有防御处理。
- 每段伤害记录伤害归属者和来源技能。爆炸、领域、持续地火不能丢失施法者归属，导致被动漏算、击杀不计或友伤。

### 6.2 倍率与叠加

每个有伤害修正的角色都要给出公式，至少标明同区相加、独立相乘、减益位置、封顶和无条件时的×1。

推荐的表达框架为：`基础伤害 × 状态修正 × 特攻区 × 宝具修正 → 防御结算 → 指定的最终修正`。这是说明格式，具体乘区由该角色设计和公共伤害流程决定，不规定所有效果都相加。

- “额外n倍伤害／n倍特攻”若表示额外加成，应写成“额外+n，总倍率×(1+n)”；不要混用“总伤害n倍”。
- 同区特攻示例：两个额外+1，结果是`1+1+1=3`，不能算×4。
- 独立特攻示例：两个独立×2，结果是×4。必须明确选择哪种，不能靠措辞猜。
- 给出无特攻、单条件、多条件、减益和边界等级的算例。文字、表格、公式冲突时先消除矛盾。
- 目标的职阶、技能、固有特性和临时骑乘状态分别判定。例如Rider职阶、拥有骑乘技能、正在骑马不能自动视为同一条件。

### 6.3 多段攻击

- 写清实体数、每实体发数、每发伤害、波次数、间隔、命中次数上限。总伤害应可复算，写明是单目标理论全中还是范围合计。
- MC受伤无敌帧是否限制多段必须明确；需要突破时，只针对该设计要求的命中，避免顺带改变其他伤害。
- “三次全中”“连续命中”必须定义计数对象、命中顺序、落空是否重置、触发后是否重置，以及计数是否跨技能／跨目标。
- 追踪必须说明锁定距离、视线、更新方式、失去目标和命中障碍物的处理。自动修正弹道不等于穿墙或必中。

## 7. 主动技能、输入与资源

每个主动技能使用统一能力卡，至少包含：输入／槽位、名称、类型、消耗、冷却、作用距离、范围、持续与时序、分段伤害、附加效果、来源、叠加规则、失败与中断、特效表现及 AI 使用条件。

- 沿用项目输入习惯，可使用蹲下左键、主副手武器、槽位0～9、长按／松开和独立飞行键。已有角色可保留其他槽位布局，不把信长的8／9号宝具位置设为全角色强制要求。
- 长按技能写清蓄力阈值、上限、即时释放效果、松开触发、MP扣除和冷却起点；切换技能、失去武器、死亡时怎样取消也要说明。
- 无目标、MP不足、冷却中或无合法位置时说明是否消耗资源。默认无合法施放条件不扣MP、不进入冷却；已经开始后被打断是否退款单列。
- 同时需要主副手支持时，客户端识别、服务端校验和武器使用入口一致；检查双手同持或重复输入不会双重扣费、双重释放。
- 百分比强化使用精确数值；例如移速+15%不能随手替换成不等价的药水等级。常驻能力与限时能力冲突时明确是否转移、保留或叠加。

## 8. 召唤物、代伤、地形与机动

| 机制 | 必须补全的设计信息 |
| --- | --- |
| 召唤物 | 数量／上限、生命、命中箱、寿命、召唤位置、跟随模式、射击节奏、被摧毁后行为、所有者与友敌判定 |
| 代伤／护盾 | 合格对象、作用半径、顺序、每次处理上限、溢出、免疫与防御先后、是否可保护他人 |
| 固定阵地／领域 | 中心、半径／高度、能否移动、进入／离开规则、重复施放和多个施法者重叠 |
| 地火／地形变化 | 伤害频率、特效、是否点燃实体／方块、是否扩散、破坏权限、到期恢复与异常退出清理 |
| 冲刺／击退 | 距离或速度、轨迹、首个／全部命中、是否穿透实体、方块碰撞和落差 |
| 飞行／载具 | 开关、平移与升降、疾跑、加速度／阻尼、悬停、碰撞、耗魔、血量、高度限制、退出与坠落保护 |

- 30生命火绳枪、6格代伤范围、120生命枪坐骑是信长专属数值，不是所有英灵召唤物的模板常量。
- 设计“地面燃烧5秒”时要明确是真实方块火，还是有火焰表现的临时伤害区域；不能产生没有说明的永久烧毁或重复灼烧。
- 用创造飞行作为手感目标时，保留生存模式、资源与碰撞规则，不能通过给玩家创造模式权限来模拟。
- 死亡、解除变身、离线、区块卸载、跨维度和服务器重载时，应定义实体、延迟任务、状态及地形的结束／恢复规则，防止残留伤害或把目标留在领域中。

## 9. 宝具

宝具单独记录真名／常用名、等级或范围等级、分类、设定来源、释放操作、MP、冷却、共享组、吟唱、分段扣费、有效范围、命中规则、特攻、额外效果、打断与结束流程。

- 使用真实设计分类，如对人、对军、对城、对神、对界、结界或支援；模型或枚举缺少该类型时记录为所需扩展，不把不认识的类型默认为对人。
- 多宝具逐一记录，不因为旧接口只有一个宝具字段就遗漏另一个，也不要求所有角色都有两个宝具。
- 写明冷却是否共享。长按固定阵地、短按跟随等模式分别描述，不沿用另一角色的默认方向。
- 宝具专属特攻只作用于该宝具的伤害。共享枪、弹丸、武器、特效资源不意味着共享宝具特攻。
- “其他不变”需要列明承接的既有行为。旧基础伤害已含特殊增益时，接入新被动要明确移除或有意保留，不能重复计算。
- 领域包括传送前记录、盟友过滤、目标存活、返场、维度不可用处理、地形恢复与施法者异常退出；特效不能替代这些效果实现。

## 10. 玩家卡与实体 AI

- 同一英灵的基础参数、被动、技能基础数值、MP消耗、冷却及宝具效果应共享定义和规则。需要NPC例外时逐项列明理由，不能因分散在不同Java类中出现两套隐藏强度。
- AI负责什么时候用、打谁、站哪里、如何选择模式。可保留基础近战、退步、闪避和演出动作；有伤害或控制的小动作仍需有记录和来源。
- 玩家与NPC的吟唱动作、寻路或操作表达可以不同，但不能额外赋予免费补枪、自动回蓝或免冷却版本。
- 决策条件区分距离、视线、目标特性、MP、冷却、环境和生命阶段；生命阶段可影响选招频率，不能未经设计改变基础伤害。
- 复用攻击归属、友敌过滤、伤害修正和召唤逻辑；客户端表现与服务端伤害分别验证。

## 11. 交付与验收

设计稿按配套模板交付，至少包含身份、参数、特性、时代、被动、专属机制、主动技能、宝具、伤害算例、AI及验收。新英灵写明新增项；重置另列保留、替换、删除的旧效果。

可直接实施前应满足：关键数值已确定；多段计数和叠加公式唯一；各项效果都有来源；资源、目标、生命周期和失败行为完整。用户尚未确定的高影响规则保留待确认，不能伪装成最终已确认规格。

实施验收至少覆盖：

1. 身份、等级符号和标签无混淆；资料引用与本地设计分开。
2. 无特攻、单特攻、叠加、减益与防御的算例正确，每种效果只计算一次。
3. 输入、长短按、主副手、MP与冷却在成功、失败、中断时一致。
4. 多实体、多段、召唤上限、破坏、溢出和友敌过滤符合设计。
5. 领域、地形、飞行在正常结束及异常退出时正确清理。
6. 相同条件下玩家卡与NPC的核心效果一致；列明必要的AI表达差异。
7. 实施代码时运行适当单元测试、GameTest、客户端和专用服务器验证；纯设计文档不声称已经通过游戏测试。

## 12. 设计审阅时应拒绝的常见问题

- “神性A是额外5倍，但总伤害乘5”，或组合示例与等级表算不一致。
